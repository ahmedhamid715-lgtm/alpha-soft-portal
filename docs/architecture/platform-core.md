# Platform Core (Module 01)

## What this module is

Alpha OS will eventually be the full operating platform for Alpha Page
Rankers — CRM, sales, client onboarding, project delivery, the SEO/GBP/
website-dev/e-commerce/GHL service modules, support, billing, AI agents,
automation, analytics, and enterprise infrastructure (70 modules total,
see the master roadmap). Module 01 is not a slice of that surface area —
it is the technical foundation every other module depends on:
configuration, database wiring, error handling, logging, validation
conventions, and a set of platform abstractions (feature flags, storage,
jobs, events, cache, pagination, search) that later modules implement
against instead of each inventing their own version.

**Nothing in this module is a business feature.** There is no login, no
CRM, no tickets, no dashboards. If you're looking for those, they don't
exist yet — see "What's deliberately not here" below.

## Why infrastructure-first

A platform this size fails one of two ways: either the foundation is
guessed at wrong early and every later module pays a rewrite tax, or
nobody builds a foundation at all and every module reinvents error
handling, logging, and config from scratch, producing 70 slightly
different conventions. Module 01 exists to make the second failure mode
structurally hard — every future module's job is to *use* what's here
(`lib/errors`, `lib/logging`, `lib/db`, `lib/platform/*`), not rebuild it.

Section 40 of the Module 01 spec asks a self-audit question worth
restating here: can Module 4 (Authentication) add real login without
rewriting the platform? Can Module 6 (Multi-Tenancy) add tenant scoping
without replacing database access? Can Module 38 (Workflow Automation)
add real triggers without replacing the event architecture? The answer
for all of these needs to be yes, and the way that's achieved is by every
platform primitive being an *interface* future modules implement against,
not a concrete choice baked into call sites. See `project-structure.md`
for where each of those interfaces lives.

## Brand

The UI is themed to Alpha Page Rankers' actual brand, extracted directly
from the live `alphapagerankers.com` site's Elementor CSS (its
`elementor-kit-14` global colors and the `.elementor-heading-title` /
`.elementor-button` font-family rules), not invented or templated:

| Token | Hex | Role |
|---|---|---|
| `brand-dark` | `#140921` | Page background (dark-mode-first) |
| `brand-dark-2` | `#1C1E29` | Card/popover background |
| `brand-dark-3` | `#26003A` | Secondary/muted surfaces |
| `brand-dark-4` | `#39195F` | Deeper accent surface |
| `brand-primary` | `#8730B4` | Primary actions, active nav |
| `brand-accent` | `#BF43FF` | Hover states, focus rings |

Typography is **Poppins** (400/500/600) — the dominant font on the live
site (headings, nav, buttons), loaded via `next/font/google` in
`src/app/layout.tsx`.

Full token architecture (primitive → semantic → component layers) lives
in `src/app/globals.css`, following shadcn/ui's variable contract so
every `src/components/ui/*` primitive picks up the brand automatically.
A real light theme, additional component variants, and the rest of
Design System polish are Module 02's job — Module 01 only establishes the
tokens and wires them through shadcn/ui's foundational primitives
(Button, Input, Card, Dialog, ...).

## Next.js 16 — read this before writing route logic

This project was scaffolded on **Next.js 16.3.1**, which has real
breaking changes from older tutorials/training data (see the repo's
`AGENTS.md`, regenerated by `next dev` — don't delete it from commits).
The one most relevant to platform work:

**`middleware.ts` is deprecated, renamed to `proxy.ts`.** The exported
function is `proxy()`, not `middleware()`. Proxy now defaults to the
**Node.js runtime** (previously Edge-only), which matters once Module 04
(Authentication) or Module 05 (RBAC) need to gate routes with logic that
touches Prisma or other Node-only APIs. No `proxy.ts` exists yet in
Module 01 — security headers are handled via `next.config.ts`'s
`headers()` function instead, since Next's own guidance is to avoid
Proxy/Middleware unless there's no other option. When Module 04 adds
route gating, create `proxy.ts` (not `middleware.ts`) at the project
root.

Also worth knowing: `next typegen` generates the route-based global types
(`LayoutProps<"/">`, `RouteContext<'/path'>`) that `tsc --noEmit` alone
can't see — that's why `npm run typecheck` runs `next typegen` first (see
`package.json`).

## What's deliberately not here

Per the Module 01 spec: no authentication, no RBAC, no CRM, no
customers/projects/tasks, no SEO/GBP/website-dev/GHL modules, no tickets,
no AI chat/agents, no billing, no employee management, no reporting.
Building any of these now — even a "quick version" — would be exactly
the premature-business-feature mistake this module exists to avoid.
Interfaces and abstractions that those modules will implement against
(storage, jobs, events, cache, search, feature flags) do exist — see
`project-structure.md` for where.

## Human boundary: the database

Prisma's infrastructure (client, schema, migration/seed scripts, error
translation, health check) is fully built and typechecks/builds without
a live database. But nobody can spin up a database on your behalf without
credentials. To make `/api/health/db` report `healthy` and start running
real migrations, set `DATABASE_URL` from your Supabase project's
connection string (see `.env.example` and `database.md` for the direct-
vs-pooled-connection distinction that matters there).
